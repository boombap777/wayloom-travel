# Wayloom Travel：旅行需求解析与本地模型部署技术方案

版本：1.0 · 整理日期：2026-09-18
实现基线：[7a936d5](https://github.com/boombap777/wayloom-travel/tree/7a936d504cadb04e028a12defa9f5c8c780c2731)

本文按实际执行的 Qwen3-1.7B 微调、当前应用代码和独立评测记录整理。历史计划见 [DEV_SPEC](../DEV_SPEC.md)，模型标注更正见[来源说明](model-provenance.md)。

## 1. 解决什么问题

用户通常用一句话描述旅行需求，但工具需要的是明确的城市、日期、人数和预算。直接让模型输出一段行程文本，难以判断它是否遗漏约束，也容易把样例价格写成实时可订信息。

本项目把任务收窄为：提取结构化需求，判断是否需要补问，只在条件齐全时调用一个受限目录工具，再返回有数据来源说明的草案。
产品提供浏览器、HTTP API 和命令行；规则解析与真实模型解析共用一套业务流程。

这是专用的结构化决策助手，不是开放式多 Agent 旅行规划系统。它没有真实票务、酒店库存或支付接口，也没有路径优化、任意天数排程和在线预订能力。

### 一次演示

输入：“从南京去杭州，10月1日出发玩三天，两个人，预算5000元，喜欢人文和美食。”
系统提取条件后查询 `demo_catalog_v1`，返回杭州样例的活动大纲、两人的演示费用和 JSON 导出入口。
若用户未说明出发日期或人数，则先追问，不提前调用目录工具。

## 2. 架构与执行流程

```text
浏览器 / HTTP API / CLI
  → TravelExtractor（rule / hf_adapter / llama_cpp 三选一）
  → TravelDecision：clarify 或 tool_call
  → 字段、动作、工具名与工具参数一致性校验
     ├─ 缺少必填字段 → 返回补问
     └─ 信息齐全 → search_trip_options → DemoTripCatalog
                                         ↓
                                DraftPlan → final_plan
```

| 模块 | 职责与实现 |
| --- | --- |
| [contracts.py](../src/travel_itinerary/contracts.py) | 用不可变 dataclass 定义请求、决策、工具调用和草案；执行类型与状态约束 |
| [extractor.py](../src/travel_itinerary/extractor.py) | 规则解析及统一 `TravelExtractor` 接口 |
| [runtime.py](../src/travel_itinerary/runtime.py) | 根据启动配置装配规则、Transformers/PEFT 或 llama.cpp 解析器 |
| [model_output.py](../src/travel_itinerary/model_output.py) | 提取 JSON、严格字段校验与唯一允许的机械修复 |
| [orchestrator.py](../src/travel_itinerary/orchestrator.py) | 处理补问，或调用目录并生成草案 |
| [catalog.py](../src/travel_itinerary/catalog.py) | 查询固定样例和计算演示预算，不访问真实供应商 |
| [web.py](../src/travel_itinerary/web.py) | 基于标准库的本机 HTTP 服务、请求校验、推理互斥与错误响应 |

编排器每次处理一个解析结果，没有多个 Agent 自由协商，也没有让模型自行执行任意函数的入口。
预算和候选内容来自受限工具；用户可见的标准补问文本由服务端生成，不直接采用模型的任意解释作为执行依据。

## 3. 数据契约与调用边界

### 3.1 八个字段

| 字段 | 含义 | 是否为调用工具的必填项 |
| --- | --- | --- |
| `departure_city` | 出发城市 | 是 |
| `destination` | 目的地 | 是 |
| `start_date` | ISO 格式出发日期 | 是 |
| `days` | 旅行天数，正整数 | 是 |
| `traveler_count` | 人数，正整数 | 是 |
| `budget_cny` | 总预算，正整数或 null | 否 |
| `themes` | 不重复的偏好列表 | 否 |
| `hotel_preference` | 酒店偏好或 null | 否 |

模型输出的 request 仍必须包含全部八个键；未提供的可选信息使用 null 或空列表。“业务上可缺省”不等于允许从模型 JSON 中省略这个键。

缺失字段不会因为有“合理默认值”就自动填入。这里的目标是提取用户条件，不是代替用户决定条件。
不过类型校验只能检查格式和内部一致性，不能证明模型提取的每个值都忠实于用户原话；后者仍要通过标注评测或用户核对验证。

### 3.2 两个模型动作、两个用户结果

- 模型动作 `clarify`：必须列出与请求实际缺失项一致的 `missing_fields`，不能附带工具调用。
- 模型动作 `tool_call`：五个必填项齐全；工具只能是 `search_trip_options`，`arguments` 必须与已校验的 request 完全一致。
- 用户结果为 `clarify` 或 `final_plan`。`final_plan` 由应用调用目录后生成，不是给模型开放的任意动作。

解析器从模型文本中提取 JSON 对象，再检查严格字段集合。未知字段、错误类型、不支持的工具、缺失必填项或参数不一致都会拒绝进入工具执行。
格式合法不等于方案有事实依据；工具和数据来源说明负责限制后续内容范围。

### 3.3 为什么允许有限修复

允许的唯一修复是：模型已经输出一个完整且通过校验的 request，但 `tool_call` 只给出了正确工具名、遗漏 `arguments` 时，复制 request 构成参数。
不推测城市、日期或人数，不修改已存在但错误的参数，也不忽略未知字段。

原始输出、修复记录和修复后结果分别保存。修复提高的是系统对一种格式遗漏的容忍度，不能把它算成模型原始输出能力。
在 120 条 GGUF 评测中，这个规则处理了 18 条遗漏；其他错误仍按失败计。

## 4. 草案生成与页面交互

当前目录只有杭州、成都、厦门、北京和西安，每个目的地一条固定方案。
先按目的地和总预算过滤，再按主题重合数、人均费用和标题排序；酒店偏好尚未用于真实酒店检索。
由于目前一城只有一条候选，主题排序没有足够候选来体现选择收益，不能据此声称已验证个性化推荐效果。

总费用是“目录中的固定人均演示预算 × 人数”，不随实际交通、酒店、季节或旅行天数变化。
返回的三项活动大纲也不会自动扩展为任意天数的每日路线。没有候选时返回无匹配说明，而不是编造库存。

浏览器仅在当前页面内存保存用户补充信息，最多携带四条历史用户消息；每条不超过 2000 字，总长度不超过 6000 字。
后端不维护长期会话数据库。重新开始或刷新会清空页面状态，模型不会获得其他用户的隐式对话记录。
调整需求从新的请求开始，避免将旧条件无提示地混入新方案。

### HTTP 接口

| 接口 | 行为 |
| --- | --- |
| `GET /api/status` | 返回选择的 profile、当前日期、目录版本和无外部写入标识 |
| `POST /api/plan` | 接受 `message` 与可选 `context`；返回 response、profile、elapsed_ms |

请求示例：

```json
{
  "message": "从南京去杭州，10月1日出发玩三天，两个人，预算5000元，喜欢人文和美食。",
  "context": []
}
```

网页实际运行模式由启动参数决定，客户端不能提交模型路径、命令、解析模式或工具指令。
服务绑定 `127.0.0.1`，检查 Host、同源 Origin、JSON Content-Type 和请求长度；HTTP body 上限为 32 KiB。
推理使用互斥锁，同时到来的另一条请求返回 `429 BUSY`，没有宣称高并发推理。

模型输出错误返回 `422 MODEL_OUTPUT_INVALID`，运行时不可用返回 `503 RUNTIME_UNAVAILABLE`；不会悄悄改用规则解析并展示成功结果。
默认日志不打印用户正文，页面静态资源与 API 均有基础响应安全头。这些是本机原型的约束，不构成公网身份认证方案。

## 5. 数据构造与 QLoRA 训练

### 5.1 数据从哪里来

`travel-v1.0` 是配置驱动的确定性合成数据：480 条训练、80 条验证、120 条冻结评测，参考日期和随机种子固定。
场景包含完整请求、可选字段稀疏请求，以及分别缺少出发地、目的地、日期、天数或人数的请求。

不同 split 使用不同模板族，并检测归一化文本的跨 split 重复；还检查期望输出能否构成合法决策、是否混入预约业务词汇，以及数据文件哈希。
但各 split 仍共享有限城市、偏好词表和生成规则，标签经过程序化校验不代表经过人工审核。
30 条人工抽检队列仍为待审核状态，不能把它写成“人工精标数据”。详见[数据血缘](data-lineage.md)。

### 5.2 实际训练配置

| 项目 | 本次已执行实验 |
| --- | --- |
| 基础检查点 | `Qwen/Qwen3-1.7B`，revision `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e` |
| 硬件 | RTX 4060 Laptop GPU |
| 量化 | 4-bit NF4、double quant、bfloat16 计算 |
| LoRA | rank 16、alpha 32、dropout 0.05、`all-linear` |
| 训练 | 4 epoch；batch size 1；梯度累积 8；学习率 0.0002 |
| 序列 | 最大 512 Token；超长样本拒绝，不静默截掉监督答案 |
| 损失 | system/user 前缀与 padding 标为 `-100`，只监督 assistant 回答 |
| HF 评测 | 相同 prompt 与聊天模板、关闭 thinking、确定性解码、最多生成 256 Token |

QLoRA 的选择服务于本机显存约束；当前只完成这一组配置的实验，没有证明 rank 16 或该学习率在所有设置下最优。
训练保存 adapter、配置、数据与权重哈希和运行清单。核对入口：[训练代码](../src/travel_itinerary/training.py)、[实际配置](../configs/training/qwen3_1_7b_travel_sft_v1.json)、[训练记录](../reports/training/qwen3-1.7b-travel-sft-v1.run_manifest.json)。

### 5.3 基础模型名称为何需要更正

原训练报告误写了 `Qwen3-1.7B-Base`。实际权重对应固定版本的 `Qwen/Qwen3-1.7B`，通过权重分片哈希核对，不能仅凭报告中的名称字符串判断来源。
这里的“base vs adapter”表示本项目 SFT 前后，而不是从纯预训练 Base 模型起步。
原始报告不改写，正确标识和核验方式单独记录在[模型来源说明](model-provenance.md)。旧的 4B 配置和 DPO 数据准备不属于已完成训练成果。

## 6. 质量与性能分别如何评估

### 6.1 120 条冻结合成集的质量

| 推理方式 | JSON 可解析 | 契约通过 | 动作匹配 | 字段 micro-F1 | 工具参数精确匹配 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 本项目微调前模型，HF | 100% | 0% | 0% | 0% | 0% |
| SFT adapter，HF | 100% | 100% | 100% | 99.88% | 98.53% |
| GGUF + LoRA，原始输出 | 100% | 68.33% | 60.83% | 79.21% | 50.00% |
| GGUF + LoRA，有限修复后 | 100% | 83.33% | 75.83% | 90.16% | 76.47% |

来源：[HF 微调前](../reports/model_eval/qwen3-1.7b-base__travel-eval-v1.0.json)、[HF adapter](../reports/model_eval/qwen3-1.7b-travel-sft-v1__travel-eval-v1.0.json)、[GGUF 全量评测](../reports/deployment/llama_cpp_full_frozen_eval_v1.json)。本次文档整理核对已有报告，未重新训练模型。

必须区分四个概念：

- JSON 可解析只说明找到了合法 JSON 对象，不代表包含要求的字段。
- 契约通过检查字段、类型、缺失项和工具参数的一致性，不代表提取值都正确。
- 字段 micro-F1 按八个字段的值匹配累计，并非自然语言生成的 Token F1；契约不通过的样本按无有效预测处理。
- 工具参数精确匹配仅统计预期调用工具的样本。HF 的 98.53% 对应 68 条中的 67 条，不是120条全部成功。

微调前 0% 是严格任务契约下的结果：例如报告首条输出能解析 JSON，但缺少 request、缺失项用中文标签表示，无法作为工具决策使用。
它不能证明原模型“不会理解旅行需求”。现有实验说明 SFT 学到了这个契约，不足以证明推荐质量、真实用户效果或全面语言能力提升。

### 6.2 为什么不能把 GGUF 降分完全归因于量化

HF 使用 bitsandbytes NF4，GGUF 使用 Q4_K_M；运行时、模板处理和解码预算也存在差异，例如当前 GGUF 配置为 `n_predict=192`，HF 为256。
因此这是两种部署配置的对比，不是只改变量化精度的严格消融实验。
应对齐 prompt 的实际字节或 Token、生成长度和推理选项，再比较未量化/量化及不同精度，才能分析各因素造成的损失。当前报告没有完成这一归因。

### 6.3 性能测量不能替代质量测量

| 实验 | 计时范围 | 样本量 | P50 / P95 | 额外说明 |
| --- | --- | ---: | --- | --- |
| HF adapter 质量评测 | Transformers 生成调用 | 120 | 22.89 / 31.91 s | 对应上表 HF 质量；不是网页 SLA |
| GGUF 早期 smoke | 新进程启动至退出，含模型加载 | 3 | 4.42 / 4.66 s | 原始契约2/3，有限修复后3/3，只证明少量样例可部署 |
| GGUF 冷启动测试 | 每次新建 CLI 进程，含模型与 LoRA 加载 | 20 | 3.54 / 4.25 s | 进程成功20/20，但修复后契约通过率为65% |
| GGUF 常驻测试 | 预热3次后，HTTP请求至完整响应 | 100 | 0.98 / 1.71 s | 请求成功100/100，但修复后契约通过率为84% |

常驻测试的生成速度 P50 为109.5 Token/s。成功收到响应、契约通过和业务正确是不同指标，不能把100/100请求成功写成任务成功率100%。
计时记录见[运行性能报告](../reports/deployment/llama_cpp_performance_v1.json)；早期 smoke 见[独立报告](../reports/deployment/llama_cpp_q4km_lora_v1.json)。

当前网页的 `llama_cpp` 解析器调用 `llama-cli`，并没有直接复用常驻 `llama-server`。
所以1.71秒不是当前网页的已验证P95。将常驻服务接入应用后，还需要测排队、解析、工具和页面交互的完整延迟。

## 7. 模型交付、运行与测试

应用通过 `rule`、`hf_adapter`、`llama_cpp` 显式选择解析器，不混用三者的运行结果。
默认规则版无需下载模型：

```shell
uv sync --frozen
uv run --no-sync travel-itinerary-web
```

打开 `http://127.0.0.1:8504/`，先使用完整示例，再使用补全示例。端口冲突时追加 `--port 8514`。

模型制品通过 [v0.1.0 Release](https://github.com/boombap777/wayloom-travel/releases/tag/v0.1.0) 独立提供，包括 Q4_K_M 基座、LoRA GGUF 和 HF adapter。
源码不内置权重，也不包含 llama.cpp 运行文件。按[发布说明](../PUBLICATION.md)解压到要求的目录、核对 SHA-256，再显式配置运行文件：

```powershell
$env:TRAVEL_LLAMA_CLI_PATH = '<llama-cli.exe的实际路径>'
uv run --no-sync travel-itinerary-web --extractor-mode llama_cpp
```

默认回归：

```shell
uv run --no-sync pytest
uv run --no-sync travel-itinerary audit-data
```

测试覆盖契约、解析、工具调用、模型失败、HTTP 请求、跨源请求及会话补全。默认测试使用离线或注入后端，不会重新执行 QLoRA、下载权重或证明真实模型质量。
训练与完整推理复现应在新的实验目录执行，保留原始报告，见[实验协议](experiment-protocol.md)与[本地部署](local-deployment.md)。

## 8. 面试追问与回答依据

**规则就能做，为什么还训练模型？**
规则是低成本、可解释的演示和回归基线；模型实验研究自然语言到固定契约的映射。现有证据只说明模型在合成分布上的表现，还不能证明在真实复杂表达上优于规则。下一步应在独立人工标注集上比较二者。

**为什么基础模型0%，微调后100%，差距这么大？**
严格契约把缺字段、字段名不一致等输出判为不可执行。基础模型JSON可解析率本来就是100%，不是完全不会回答。这里主要反映格式与任务约束适配，不能直接解释成理解能力从0提升到100。

**有限修复是不是改分数？**
它是应用中的确定性适配，但必须分别报告原始和修复后分数，并保留每条修复记录。没有改变标签、填补事实槽位或把失败样本删掉；如果只展示修复后结果，就会夸大模型本身的能力。

**为什么选 QLoRA，rank 16 有什么依据？**
目的是在笔记本 GPU 上完成可复现的任务微调。rank16是已运行的一组配置，不是搜索后的最优值。若要论证性能/显存最优，需要同一数据和训练预算下的 rank、目标层与精度消融。

**这是一个真正的旅行规划 Agent 吗？**
它完成有限补问、一次受限工具调用和草案返回。当前没有路线求解、地图或实时供应商，目录还是一城一方案。应称为旅行需求解析与草案助手，不应声称完整个性化旅行规划。

**类型校验能解决幻觉吗？**
不能。它防止错误格式或不一致参数进入工具，但一个格式合法的城市或预算仍可能不是用户说的。需要更有代表性的标注集、字段来源核对，以及执行高风险动作前的用户确认；本项目目前根本不提供预订写入。

**快到1.71秒，能直接拿来做网页服务吗？**
那是常驻服务的顺序请求P95；当前网页用CLI，且常驻测试的契约通过率并非100%。要先接入相同常驻后端并复核质量，再测整个HTTP应用和并发条件。
